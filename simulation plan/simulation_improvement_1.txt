2.2 Implement leakage-safe dataset splitting
Use three logically separate datasets:
Training
Normal + known attack classes

Train the existing supervised Random Forest using the known classes. Train the existing autoencoder using only approved normal samples.


Calibration
Normal-only validation samples

Determine the anomaly threshold using normal validation data. Freeze the threshold before evaluation.


Testing
Normal + known attacks + held-out attack class

Run predictions without exposing the ground-truth labels to the detector.


For Leave-One-Class-Out (LOCO), repeat the experiment for each eligible attack class. A held-out class must be excluded from training, preprocessing decisions that use labels, and threshold calibration.
2.3 Resolve the existing HAI data issue first
The repository's dataset report identifies two reproducibility blockers:
- The original HAI source-file lineage is not independently verified.
- models/standard_scaler.joblib is missing.
Restore or regenerate the scaler from a verified training-only pipeline, preserve the original dataset source and checksums, and verify the 66-feature order before claiming reproducible OT results.

Deliverable: A repeatable experiment pipeline that can produce a train/calibration/test manifest for every run.

4.1 Simulation state machine
Use these states:
READY

Configured / idle


RUNNING

Processing events


PAUSED

Clock frozen


STOPPED

Run terminated



RESTART creates a new run and returns the controller to READY. It must not erase the archived run.

Action	Allowed starting state	Result
Start	READY	RUNNING
Pause	RUNNING	PAUSED
Resume	PAUSED	RUNNING
Stop	RUNNING / PAUSED	STOPPED
Restart	Any state	Archive old run, create new READY run

4.2 Define button functions
Each button should call a controller method rather than containing its own simulation logic.
controller.start()controller.pause()controller.resume()controller.stop()controller.restart()controller.set_speed(2)



The controller is responsible for validating state transitions, maintaining the simulation clock and updating the run record.
4.3 Event scheduler
The scheduler should:
1. Read the next eligible event from the selected dataset.
2. Respect the configured playback speed.
3. Dispatch events only when the state is RUNNING.
4. Track the current event index.
5. Stop dispatching when the dataset is exhausted.
6. Preserve the current position when paused.
7. Save the last processed position when stopped.
Use a configurable batch size so a large dataset does not freeze the Streamlit interface.

Important Streamlit consideration: Streamlit reruns the application when controls are clicked. Store controller state in st.session_state and persist run metadata separately. Avoid starting uncontrolled background threads from button callbacks.

There are two important integration details:

First: Ground-truth isolation.

The existing detection workspace in src/ui/views.py currently displays ground-truth labels during individual row inspection. The new research simulation must not follow that pattern. The event processor should extract labels into a separate evaluation record and pass only timestamp, features and permitted context to the detector.

Second: Zero-Trust policy evaluation.

DetectionService.detect() currently calculates risk and stores the event. It does not itself invoke evaluate_zero_trust_decision(). The new simulation orchestration should explicitly invoke that existing evaluator after detection and associate its verdict and rule traces with the event. Keep this advisory: the existing implementation sets is_automatic_action=False.
5.2 Extend event storage safely
Do not delete or recreate the existing SQLite database.

Add a migration for new research fields or separate research tables.

Link existing event records using run_id where appropriate. Keep existing alert records and review history intact.

For a research experiment, store both the model prediction and the ground-truth class in the evaluation layer, not in the detector's input or feature payload.

Essential button acceptance tests
- Start from READY → RUNNING.
- Start from RUNNING → rejected.
- Pause from RUNNING → PAUSED.
- Pause from READY → rejected.
- Resume from PAUSED → RUNNING.
- Stop from RUNNING → STOPPED.
- Restart after STOPPED → new run ID and READY.
- Change speed → scheduling interval changes without changing predictions.
- Complete dataset → run becomes COMPLETED automatically.

11. Important decisions to finalize before coding
There are three technical decisions I would not leave ambiguous:
1. IT novelty detection: The IT Autoencoder inference path is optional and requires its 79-feature artifact. The 77-feature configuration does not automatically provide an independent AE novelty detector; verify availability before designing the IT experiment.
2. HAI reproducibility: Resolve the missing scaler and training-source provenance before retraining or claiming new final metrics.
3. Dashboard metrics: Display metrics from the current experiment run, not aggregate historical SQLite alerts. Never mix old alerts with current experiment TP/FP/TN/FN.
Also, describe LOCO as unseen attack-class generalization or zero-day-like evaluation, not proof of real-world zero-day detection.
