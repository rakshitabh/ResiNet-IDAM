Phase 2 – Dataset preparation and leakage-safe splitting
Highest research priority
This phase establishes whether your unseen-attack evaluation is scientifically valid.
2.1 Prepare IT and OT datasets independently
IT – IDS2025
- Identify all attack classes available in the dataset.
- Identify normal traffic.
- Verify feature columns and target-label columns.
- Remove identifiers and labels from model inputs.
- Check class distribution and missing values.
OT – HAI
- Retain the existing 66 ordered process features.
- Exclude timestamp and attack labels from model input.
- Verify the existing train/test dataset lineage.
- Verify the scaler was fitted using training data only.
- Preserve timestamps and labels separately for evaluation.
Do not merge IT and OT features into a single training matrix. Their feature schemas and datasets are different.
2.2 Create three separate data partitions
Training set
Model fitting

- Normal samples.
- Known attack classes.
- For RF: normal + known attack labels.
- For AE: normal-only samples.


Calibration set
Threshold setting

- Normal-only validation samples.
- Used to determine anomaly thresholds.
- Never use held-out attack samples to tune the threshold.


Test set
Final evaluation

- Normal test samples.
- Known attack test samples.
- Held-out unseen attack classes.
- Ground-truth labels kept separate from inference.


2.3 Implement Leave-One-Class-Out (LOCO)
For every eligible attack class:
1. Select one attack class as the held-out class.
2. Remove every sample of that class from training.
3. Remove it from threshold calibration.
4. Train the model using the remaining permitted data.
5. Freeze the model and threshold.
6. Test using normal traffic and the held-out class.
7. Evaluate predictions against the hidden ground truth.
8. Repeat for the next eligible attack class.
Example:
Experiment	Training attack classes	Held-out class
LOCO-01	All except DoS/DDoS	DoS/DDoS
LOCO-02	All except PortScan	PortScan
LOCO-03	All except BruteForce	BruteForce
LOCO-04	All except Botnet ARES	Botnet ARES
LOCO-05	All except Infiltration	Infiltration

These are experiment examples. Confirm the actual class names and sample counts from the audited datasets before generating the final experiment matrix.
2.4 Prevent preprocessing leakage
All fitted preprocessing operations must follow this rule:
- Fit scaler on training data.
- Fit imputer on training data.
- Perform feature selection on training data.
- Transform calibration and test data using the fitted training artifacts.
- Never refit using test data.
Deliverables:
data/
└── evaluation/
    ├── manifests/
    ├── splits/
    │   ├── it/
    │   └── ot/
    └── metadata/


Acceptance criteria:
- No held-out attack class occurs in training or calibration.
- Test labels are unavailable to the detector.
- Feature transformations are fitted on training data only.
- Every split is reproducible from a saved manifest and seed.

Phase 3 – Strengthen the existing detector implementations
Goal: Reuse the existing algorithms. Do not introduce an unnecessary new algorithm.
3.1 IT detector – IDS2025 Random Forest
Continue using the existing Random Forest implementation.

Its role:
- Recognize normal traffic.
- Classify known attack classes.
- Provide the supervised baseline.
Important limitation: Random Forest is a closed-set classifier. It can assign an unseen attack to an existing known class or Normal. Its output alone does not establish novelty detection.
3.2 IT Autoencoder
Use the existing optional IT Autoencoder path only when:
- The required weights exist.
- The exact 79-feature schema is supported.
- The preprocessing pipeline is compatible.
- The threshold is calibrated and frozen using normal-only validation data.
The existing 77-feature path can fall back to Random Forest when the AE artifact is unavailable. Do not present that fallback as Autoencoder-based novelty detection.
3.3 OT detector – HAI Autoencoder
Continue using the existing HAI Autoencoder:
- 66 ordered input features.
- Reconstruction error calculation.
- Normal-only threshold calibration.
- Prediction based on reconstruction error against the frozen threshold.
The OT detector should not receive the ground-truth attack label during inference.
3.4 Standardize detector outputs
Define one consistent output contract for the simulation and evaluation layers.

Example:
{    "source": "OT",    "detector_name": "HAI Autoencoder",    "prediction": "ANOMALY",    "is_anomaly": True,    "anomaly_score": 0.91,    "threshold": 0.82,    "confidence": None,    "feature_schema_version": "hai-66-v1",    "model_version": "model-version-id"}



confidence should remain unavailable if the detector does not provide a meaningful calibrated confidence score. Do not manufacture it.

Acceptance: Every detector uses its own documented decision rule. No generic second threshold is applied on top of an already-computed detector decision.
Phase 4 – Separate inference from ground-truth evaluation
Critical implementation change
This is the most important correction to PR #7.
4.1 Correct the CSV parser
Current file:

src/simulation/data/csv_parser.py

The current parser can infer a ground-truth label from expected_outcome, and it defaults missing labels to Normal.

Remove both behaviours.

Use separate fields:
Field	Meaning	Used by
expected_outcome	Expected Zero-Trust policy verdict	Policy evaluation
ground_truth_label	Actual dataset attack label	Evaluation only
telemetry_record_id	Reference to empirical feature row	Telemetry resolver
prediction	Model-generated result	Evaluation after inference

If a ground-truth label is missing, mark it as unavailable. Do not treat it as Normal.
4.2 Introduce separate data objects
Recommended design:
SimulationEvent
      |
      ├── InferencePayload
      |       ├── source
      |       ├── telemetry_record_id
      |       ├── identity/device context
      |       └── permitted features
      |
      └── EvaluationRecord
              ├── ground_truth_label
              └── attack_class


Suggested new module:

src/evaluation/models.py

The detector should receive only the inference payload.

The evaluator should receive the prediction and the evaluation record after inference is complete.
4.3 Correct the execution order
The required execution order is:
1. Load event
2. Resolve empirical features
3. Construct inference payload
4. Invoke detector
5. Store prediction
6. Retrieve evaluation label
7. Compare prediction with ground truth
8. Calculate TP / FP / TN / FN
9. Calculate Zero-Trust risk
10. Evaluate policy
11. Persist results


The detector must never access the evaluation label.

Acceptance tests:
- Changing ground_truth_label does not change detector output.
- Changing expected_outcome does not change detector output.
- Missing ground truth is not counted as a true negative.
- Ground truth is not passed to the detector.

- Detection latency.
- Event-level and attack-episode-level metrics where timestamps and labels support them.
For imbalanced datasets, do not rely on accuracy alone.
5.4 Handle evaluation edge cases
Implement explicit handling for:
- No positive samples.
- No negative samples.
- No detector prediction.
- Missing ground-truth labels.
- Failed events.
- Cancelled events.
- Duplicate sample IDs.
- Very small held-out attack classes.
For example, if a test set has no actual attack samples, recall is undefined for that test set. Do not silently report it as a meaningful zero.

Deliverable: A reusable evaluation engine that can evaluate the IT and OT detectors independently and execute repeatable LOCO experiments.

6.2 Improve the TelemetryResolver
Current:

src/simulation/data/telemetry_resolver.py

The current implementation dynamically drops selected columns and treats the remaining columns as features. This is not sufficiently safe.

Required:

src/simulation/engine/controller.py

RUNNING	Pause	PAUSED
PAUSED	Resume	RUNNING
RUNNING	Stop	STOPPED
PAUSED	Stop	STOPPED
STOPPED	Restart	READY
RUNNING	All events completed	COMPLETED

Do not restart an old scheduler by simply calling Start again.

7.1 Keep detection and Zero-Trust separate
These are different questions:
- Intrusion detection: Is this event anomalous?
- Zero-Trust assessment: Given the identity, device, asset and behaviour, what should the system recommend?
An event can be anomalous but receive a different policy recommendation depending on its context.
7.2 Required execution flow
Detector
   |
   ├── Normal / Anomaly
   |
   └── Anomaly severity
            |
            v
      Five-factor Risk Engine
            |
            v
      Zero-Trust Policy Engine
            |
            v
      ALLOW / REQUIRE VERIFICATION / DENY


7.3 Separate reporting
Do not use policy verdicts as attack-detection ground truth.

Report these independently:

Detection metrics
- Precision
- Recall
- F1
- FPR
- FN
- TP
Zero-Trust metrics
- Risk-score distribution.
- ALLOW / REQUIRE VERIFICATION / DENY distribution.
- Policy decision agreement with expected policy outcomes, where such expectations are independently defined.
- Risk-factor contribution analysis.
All policy actions must remain advisory in the simulation. No real industrial control action should be triggered.

Critical experimental rules
- Do not mix IT and OT performance into one score without a clearly defined fusion experiment.
- Do not claim a real-world zero-day detection capability from synthetic held-out-class evaluation.
- Report the number of samples in every test class.
- Clearly disclose small sample sizes.
- Include missed attacks, not just detected attacks.
- Use confidence intervals where the sample size supports meaningful estimates.
- Keep the historical baseline results separate from newly measured results.

My strongest recommendation
Build the project around three clearly separated layers:
1. Detection layer: Existing IDS2025 and HAI algorithms identify anomalies.
2. Evaluation layer: Measures whether the detector correctly identified attacks, including unseen attack classes.
3. Zero-Trust layer: Uses identity, device, asset and behavioural context to recommend access decisions.
