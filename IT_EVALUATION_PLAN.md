# ResiNet-IDAM: IT Intrusion Detection Model Reliability & Evaluation Plan

## Adaptive Deep Learning and Zero-Trust Framework for Detecting Zero-Day Intrusions in IT-OT Hybrid Critical Infrastructures

---

## 1. Executive Summary

ResiNet-IDAM aims to protect IT-OT hybrid critical infrastructures by combining IT intrusion detection with OT anomaly detection, reinforced by Zero Trust principles and IT-OT cross-domain event correlation.

The current focus is establishing a **rigorous, reliable IT intrusion-detection model**. While initial supervised baseline results on `IDS2025.xlsx` show an impressive **99.56% test accuracy** and **96.76% macro F1-score**, these headline metrics do not yet demonstrate robust generalization to unseen real-world network traffic or novel zero-day threats. 

This document establishes the formal roadmap and technical criteria required to transform the current baseline into a scientifically sound, leakage-resistant, and zero-day-capable intrusion detection engine.

## 3. Critical Limitations & Identified Vulnerabilities

1. **Severe Class Imbalance in Critical Attack Vectors:**
   * The `Infiltration` class contains only 29 total instances in the entire dataset, with just 6 instances in the test partition.
   * A recall of 66.67% represents only 4 correctly classified samples out of 6. A misclassification of 1 or 2 flows dramatically shifts the score, meaning high overall accuracy masks critical blind spots.
2. **Insufficiency of Exact Overlap Check:**
   * Checking for exact duplicate feature vectors (`overlap == 0`) does not preclude near-duplicate flows, repeated packet exchanges within the same TCP conversation, or traffic generated by the same attack script run across seconds.
3. **Feature Leakage and Shortcut Learning:**
   * Features such as `Source Port` and `Destination Port` are included in the 79 feature columns. In synthetic or benchmark datasets, attack tools often bind to fixed source/destination ports, allowing classifiers to achieve artificial near-100% accuracy simply by memorizing port numbers rather than behavioral network dynamics.
4. **Absence of Temporal or Session Grounding:**
   * If random stratified sampling was applied to flows that share an underlying session, flows from the same attack burst appear in both training and testing sets, violating independence assumptions.
5. **Unsubstantiated Zero-Day Detection Claims:**
   * The existing Random Forest is a 7-class closed-world supervised classifier. It is trained on known labels and tested on the exact same label set. This setup evaluates closed-set classification, not zero-day or novel intrusion detection.

## 4. Comprehensive Reliability Roadmap (What Must Be Done)

### Step 1: Verify Dataset Provenance & Feature Semantics
* **Trace Origin:** Determine the exact benchmark origin of `IDS2025.xlsx` (e.g., CIC-IDS2017 derivative, CSE-CIC-IDS2018, or custom simulated captures).
* **Metadata & Grouping Audit:**
  * Check if timestamp, flow identifier, capture day, or host IP fields exist in raw files or can be recovered.
  * Document any missing provenance without making unverified assumptions.
* **Feature Sanity Audit:**
  * Inspect the role of identity-like features (`Source Port`, `Destination Port`, `Protocol`).
  * Determine whether port features act as shortcut predictors rather than genuine behavioral indicators.

### Step 2: In-Depth Data Leakage Investigation
* **Near-Duplicate Detection:**
  * Quantify feature similarity between training and testing flows using nearest-neighbor / distance metrics to detect near-identical flow vectors.
* **Flow Key & Session Sharing:**
  * Check whether concurrent flows from identical communication pairs leaked across the 80/20 split.
* **Single-Feature Predictive Power:**
  * Test individual feature predictive capacity to spot any single feature capable of trivially separating attack classes (a hallmark of synthetic label artifacts).

### Step 3: Realistic, Leakage-Resistant Evaluation Split
* **Group / Temporal Splitting:**
  * If capture days, timestamps, or session identifiers are available, split partitions strictly across time or capture sessions rather than random stratified sampling.
  * If time fields are unavailable, construct a defensible split strategy (e.g., grouping by subnet, flow duration clusters, or feature-restricted subsets) and document the constraints explicitly.
* **Preprocessing Isolation:**
  * Maintain strict isolation: fit all imputers, scalers, and encoders solely on the training partition and transform validation/test sets out-of-sample.

### Step 4: Granular Multi-Class & Rare-Attack Evaluation
* **Multi-Metric Assessment:**
  * Move beyond overall accuracy. Report per-class Precision, Recall, F1-Score, False Positive Rate (FPR), and full Confusion Matrices.
* **Dedicated Rare-Class Scrutiny:**
  * Evaluate specialized handling for minority classes like `Infiltration` and `Web Attack` (e.g., cost-sensitive loss, SMOTE/ADASYN for training only, or threshold tuning).
* **Operational False-Positive Analysis:**
  * Measure normal traffic false-alarm rate (Benign FPR), which is critical for preventing alert fatigue in operational SOC/OT environments.

### Step 5: Independent Generalization & True Zero-Day Testing Protocol
* **Leave-One-Class-Out (LOCO) Evaluation:**
  * Systematically hold out one or more entire attack categories (e.g., train on Normal + 5 attack classes, withhold `Infiltration` or `Botnet ARES` completely from training).
  * Evaluate whether the detection engine flags the withheld class as an anomaly or malicious deviation.
* **Transition to Hybrid Supervised / Anomaly Detection:**
  * Combine the multi-class classifier with an unsupervised or semi-supervised anomaly detector (e.g., Autoencoder, One-Class SVM, or Mahalanobis distance) to flag flows that deviate from learned normal and known-attack distributions.
* **Cross-Scenario / Cross-Dataset Testing:**
  * Evaluate the model on external flow datasets with aligned feature schemas to test true domain generalization.
